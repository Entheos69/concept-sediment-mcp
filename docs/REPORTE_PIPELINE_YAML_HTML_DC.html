Concept-Sediment · CodeMCP · Reporte Técnico · 2026-06-10

Pipeline de consumo de YAMLs:
anatomía de la sedimentación

Mapa función-por-función desde process_session.sh hasta las tools cs_* del MCP server. Con glosario, justificación de cada decisión de diseño, ejemplos, contraejemplos, contraste tautológico contra el propio grafo, y proyecciones del sistema.

§1 · JUSTIFICACIÓN — POR QUÉ EL PIPELINE ES ASÍ

Tres decisiones cargan todo el peso

D1La base de datos compartida ES el contrato de integración
No existe API de ingesta ni "envío al MCP server". El pipeline Django (local) y el MCP server (Railway) leen y escriben el mismo Postgres+pgvector. Al hacer COMMIT la transacción de extract, cualquier cs_search_concepts ya ve los datos.
FundamentoElimina una capa entera de serialización, versionado de API y sincronización. El precio: el schema de las tablas graph_* se vuelve contrato público — toda migración es un cambio de interfaz entre dos repos (de ahí el gate G3 de CLAUDE.md).
D2Orquestador shell delgado + comandos Django idempotentes
process_session.sh no contiene lógica de negocio: hace pre-flight, watchdogs y secuenciación. Cada fase (extract, decay, fracturas, embeddings, índices) es un manage.py invocable por separado.
FundamentoEsa separación es lo que habilita los modos --fast / --maintenance / --skip-decay y la reparación manual paso a paso cuando algo truena. Un monolito no permitiría procesar 3 YAMLs con un solo mantenimiento final.
D3Nunca descartar en silencio ya sedimentado
Toda discordancia (relación con tipo desconocido, target inexistente, validación fallida) se captura en RelationDiscard con razón estructurada y ruta de reconciliación.
Grano de tautologíaEsto no es un hallazgo de este mapeo: es el "Axioma de no-descarte de discordancias schema-YAML" (principle activo, decisión B1.1 alfa del Guardian, 2026-05-05) ya sedimentado en el grafo. El código de extract_concepts.py es su implementación literal.
La forma del sistema

El pipeline es un compilador de memoria: el YAML es código fuente, el pre-flight es el linter, extract es el parser+linker (resuelve referencias), decay/promoción son el optimizador (recalcula pesos con el tiempo), y los embeddings son el índice del binario. El MCP server es el runtime que lo ejecuta como consultas.

§2 · GLOSARIO

Vocabulario del sistema

sedimentación
Proceso de convertir el conocimiento de una sesión de trabajo (YAML de cierre) en nodos y aristas persistentes del grafo. Metáfora geológica: las capas se acumulan y consolidan con el tiempo.
concepto (Concept)
Nodo del grafo. Tiene name único (≤200 chars), type evolutivo, status, weight, description, dominios, proyectos y un vector embedding de 1536 dimensiones.
depth
Cómo se usó el concepto en la sesión — NO qué es. Valores: mention (referenciado), usage (aplicado), decision (informó una decisión). Cada uno aporta un delta de weight distinto.
type (event / pattern / principle)
Madurez del concepto. NO se declara en el YAML: el sistema lo infiere y lo promueve automáticamente según frecuencia, profundidad y span temporal.
weight
Score acumulado del concepto. Sube con cada ocurrencia productiva (ponderada por depth). Conceptos con weight ≥ 2.0 son principios consolidados: no contradecirlos sin consultar al Guardian.
occurrence (ConceptOccurrence)
Registro de que un concepto apareció en una sesión concreta, con su depth, proyecto, contexto y metadata YAML cruda. Es la unidad de evidencia.
decay
Envejecimiento temporal: conceptos sin menciones recientes transitan active → dormant → archived, modulado por densidad del dominio y amortiguador por weight. Los principle no decaen.
promoción
Ascenso de type: event→pattern (3+ ocurrencias, 1+ usage, span ≥7 días); pattern→principle (8+ ocurrencias, 2+ decisions, span ≥30 días). Solo cuentan ocurrencias productivas.
fractura
Alerta inmunológica: un concepto debilitado por decay (dormant/archived) que aún tiene dependientes activos. Señala cimientos que se duermen bajo estructuras vivas.
vacuna
Concepto sedimentado que codifica una directiva contra un failure mode conocido. cs_get_alerts reporta las vacunas esperadas que faltan en el grafo.
RelationDiscard
Captura estructurada de una relación que no pudo sedimentar (tipo desconocido o target no encontrado). Queda pending hasta reconciliación caso por caso.
RelationAlias
Tabla de reconciliación de grafía: mapea un alias de relación (ej. resolved_by) a su tipo canónico, con posible inversión de dirección (flip).
smoke / is_test
Sesión de prueba E2E. Declara status: smoke_test en el YAML; sedimenta con SessionLog.is_test=True: persiste para forensia pero queda excluida de weight, promoción, decay y queries productivas (axioma F47-D1).
FULL / LIGHT
Decisión automática del script por día calendario: la primera corrida del día es FULL (pipeline completo); las siguientes son LIGHT (sin decay ni fracturas, que solo tienen sentido una vez al día).
cuarentena selectiva
Política del pre-flight batch: los archivos que fallan checks NO procesan, los que pasan SÍ, con reporte explícito de razones y advertencia sobre relaciones cruzadas hacia archivos en cuarentena.
SessionLog
Registro de procesamiento por session_id. Es la pieza que da idempotencia al pipeline y la que porta el flag is_test.
Humandato
Subsistema de alertas (fracturas + vacunas faltantes). Su salida en archivo es ALERTAS_HUMANDATO.md; su salida viva es cs_get_alerts.

Después detect_fractures → ALERTAS_HUMANDATO.md. Orden obligatorio: decay antes de fracturas (se calculan sobre weights ya decaídos).

Fase 2.7 — Embeddings (corre SIEMPRE: FULL y LIGHT)

El extract deja embedding = NULL; este paso es un backfill desacoplado. SQL raw porque el ORM no soporta el tipo vector. Tu comando manual generate_embeddings --status active ejecuta exactamente este código — es el complemento necesario tras un batch --fast + --maintenance (que NO genera embeddings, el propio script lo advierte).

§5 · EJEMPLOS Y CONTRAEJEMPLOS

Lo que sedimenta y lo que no

Ejemplo 1 — YAML que procesa limpio

concept_sediment:
  session_id: "2026-06-10-001-CodeMCP"
  project: "concept-sediment-mcp"
  domains_active: [mcp_architecture]
  concepts:
    - name: "BD compartida como contrato de integracion"
      depth: decision
      domains: [mcp_architecture]
      related_to:
        - target: "sedimentacion de conceptos"
          relation: instance_of
      notes: "El schema graph_* es la interfaz publica entre repos."
  status: reviewed

Pasa los 7 checks → extract crea/refuerza el nodo, la relación resuelve por nombre, SessionLog sella, y el siguiente generate_embeddings lo hace buscable semánticamente.

Contraejemplo 1 — cuarentena en pre-flight (ni toca la BD)

status: draft           # CHECK 2/7 FAIL: se requiere reviewed
depth: applied          # CHECK 3/7 FAIL (lint): depth invalido, validos mention|usage|decision
name: "(212 caracteres...)" # CHECK 3/7 FAIL: name es identificador, no descripcion → mover a notes
concept_sediment_mcp:   # parse FAIL: clave raiz debe ser concept_sediment

La cuarentena es selectiva: en un batch, los demás archivos sí procesan, con advertencia explícita de que las relaciones hacia conceptos de archivos en cuarentena quedarán como targets fantasma.

Contraejemplo 2 — la relación que NO muere en silencio

related_to:
  - target: "concepto que nadie escribio"
    relation: structurally_analogous   # no esta en RELATION_MAP ni en RelationAlias

# resultado:
[audit] discard_capture: unknown_type -- structurally_analogous -> concepto que nadie escribio
→ RelationDiscard(reason=UNKNOWN_TYPE, status=pending)  # reconciliable, auditable

Evidencia viva: hoy el sistema tiene 25 discards pendientes (12 unknown_type + 13 target_not_found, el más antiguo de 29 días) — exactamente el caso de uso del ciclo de reconciliación caso-por-caso ya definido en el grafo ya sedimentado.

Contraejemplo 3 — el smoke que persiste pero no contamina

status: smoke_test     # CHECK 2/7: [OK SMOKE] — no contamina queries productivas (F47-D1.1)

# add_occurrence con is_test=True:
occurrence creada           → persiste (forensia)
weight / last_seen / projects → NO se actualizan
promocion / decay           → NO cuenta (solo _productive_occurrences)
queries cs_* del MCP        → excluido (COALESCE(sl.is_test, FALSE))

Contraejemplo 4 — el falso "ya procesado" (failure mode corregido)

Antes del fix F47-D1: una migración no aplicada producía ProgrammingError en is_processed; el except solo atrapaba OperationalError, Python salía con exit 1, y el script lo leía como "YA PROCESADO" — el YAML quedaba en cuarentena sin haber sedimentado nunca. La lección portable: en protocolos de exit code, el estado de error debe ser distinto del estado negativo, y el handler debe capturar la clase padre de excepciones.

§7 · MEJORAS Y PROYECCIONES

Hacia dónde puede crecer

Cada propuesta marcada según el contraste de §6: ya en el grafo = retomarla, no re-descubrirla · nueva = sin representación previa detectada (lenguaje de incompletitud: "no encontrada", no "no existe").

M1Reactivar entity resolution híbrido archived + fractura
Hoy la identidad de conceptos es name__iexact + slug: "BD compartida" y "base de datos compartida" crean nodos duplicados. El diseño por embedding (≥0.92 mismo concepto, 0.75–0.91 ambiguo → confirmación) ya existe como concepto archivado en fractura crítica. La infraestructura (pgvector + find_similar_concepts()) ya está escrita y sin uso en el hot path.
Por qué primeroEs la fractura con más palanca: cada duplicado erosiona weight (se reparte entre gemelos), promoción y búsqueda. Reactivarla además resuelve parte de los 13 discards target_not_found (targets con grafía distinta).
M2Decay consciente de genealogía dirección decidida
El decay actual es ciego: cada concepto envejece solo, y una fundación viva se duerme aunque algo encima respire — eso ES la fractura. La dirección ya está sedimentada (2026-06-06): propagar actividad hacia arriba por aristas de dependencia. Falta el mecanismo (fracción de refuerzo, profundidad de propagación, anti-ciclos).
M3Batch real de embeddings nueva
backfill_embeddings hace 1 request HTTP por concepto (el batch_size actual solo agrupa logging). La API de OpenAI acepta listas en input: un batch de 100 textos por request reduciría latencia y costo del paso 2.7 en ~100×. Cambio acotado a graph/embeddings.py.
M4Flag --cron no interactivo prevista en el código
El prompt interactivo [y/n] del pre-flight bloquea automatización (el propio script lo anota: "Cron futuro requerira flag --cron"). Con él, el pipeline podría correr nocturno: batch de reviewed pendientes + maintenance + embeddings sin humano presente.
M5Sedimentación del estado de deudas (cerrar la tautología inversa) nueva
El caso F47-D1.2 (deuda pagada en código, viva en el grafo) sugiere un mecanismo: cuando un YAML declara una relación resolves hacia un concepto-deuda, el sistema ya suprime alertas — pero nada detecta deudas resueltas sin sedimentación. Proyección: un check de mantenimiento que liste conceptos-brecha (eventos con "deuda"/"brecha" en el nombre) sin relación resolves entrante, para revisión del Guardian.
M6Receta portable — qué llevarse a otra solución
Los siete componentes mínimos del patrón, ordenados por valor: (1) una sola BD como contrato escritor-batch/lector-online; (2) orquestador delgado + fases idempotentes invocables por separado; (3) pre-flight en cascada barato→caro con cuarentena selectiva; (4) idempotencia por tabla de registro (update_or_create + check de 3 estados); (5) embeddings como backfill desacoplado (WHERE embedding IS NULL); (6) nunca descartar en silencio — tabla de discards reconciliable; (7) flag is_test en origen, excluido de todos los agregados.
Regla de oroLa ingesta nunca debe bloquearse por el servicio más frágil (el provider de embeddings): por eso (5) es backfill y no parte del extract.
